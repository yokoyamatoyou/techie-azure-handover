# Human Resonance Algorithm - アルゴリズム説明書

## 1. 設計思想

### 1.1 従来アプローチとの違い

| 観点 | 従来（統計言語学ベース） | 本アルゴリズム |
|------|--------------------------|----------------|
| 目標 | AIらしさを消す（回避型） | 人間らしさを生む（創出型） |
| 手法 | n-gram分布、Zipf分布適合 | 心理学・語用論・修辞学 |
| 評価 | AI検出ツール回避率 | 読者の共感・興味・信頼 |

### 1.2 3軸モデル

本アルゴリズムは「共感」「興味」「人間味」の3軸でテキストを評価・加工する。

```
                    読者の心
                       │
        ┌──────────────┼──────────────┐
        │              │              │
     共感            興味           人間味
   (Empathy)     (Curiosity)     (Humanity)
        │              │              │
   感情心理学      認知心理学      心理言語学
   ナラトロジー      修辞学        発達心理学
     語用論        談話分析       社会言語学
```

## 2. パイプライン構成

### 2.1 処理フロー

```
入力テキスト
    ↓
Phase 0: Persona Lock ────── 一人称・口癖の固定
    ↓
Phase 1: Empathy ─────────── 共感要素の注入
    ↓
Phase 2: Curiosity ───────── 興味を引く構造の設計
    ↓
Phase 3: Humanity ────────── 人間らしい揺らぎの付与
    ↓
Phase 4: Rhythm ──────────── 文のリズム・テンポ調整
    ↓
Phase 5: Editor ──────────── 編集者視点の校正 + ファクトチェック
    ↓
Phase 6: Legal ───────────── 法務リスクの確認・修正
    ↓
Phase 7: Sanitize ────────── 禁止フレーズ・インジェクション除去
    ↓
Phase 8: Platform ────────── note/LinkedIn向け最終調整
    ↓
出力テキスト
```

### 2.2 モジュールと責務の対応（1モジュール1機能）

各 Phase は**1つの役割**に寄せて設計されている。対応は以下のとおり。

| モジュール | 役割（1つ） | 備考 |
|------------|-------------|------|
| **pipeline.py** | パイプラインの統合実行 | Phase の順次実行・設定・結果の集約のみ。処理ロジックは各 Phase に委譲。 |
| **phase0_persona.py** | ペルソナ固定 | 一人称・口癖の決定と注入。 |
| **phase1_empathy.py** | 共感注入 | 脆弱性・感情ミラー・呼びかけの配置。 |
| **phase2_curiosity.py** | 興味設計 | 情報ギャップ・オープンループ・文の並べ替え。 |
| **phase3_humanity.py** | 人間味付与 | 言い直し・曖昧さ・脱線・カジュアル表現。 |
| **phase4_rhythm.py** | リズム・テンポ調整 | 文長の揺らぎ・段落バランス・接続詞の単調さ軽減。 |
| **phase5_editor.py** | 編集者校正 **＋ ファクトチェック** | **2責務を1モジュールに集約**。文体・一人称・言い回しの揺らぎ（編集）と、数字・固有名詞のソース照合（ファクト）を「編集者フェーズ」としてまとめている。 |
| **phase6_legal.py** | 法務リスクの検出・修正 | 景表法・薬機法・金商法などのパターン検出と置換。 |
| **phase7_sanitize.py** | 禁止フレーズ・インジェクション除去 | 定型句削除とメタ指示の除去。 |
| **phase8_platform.py** | プラットフォーム最適化 | note / LinkedIn の2種を「プラットフォーム適応」という1責務のバリエーションとして扱う。 |

**Phase 5 について**: 編集者校正（文体・一貫性・表現の揺らぎ）とファクトチェック（事実の照合）は**関心が異なる**が、パイプライン上は「編集者が見る品質」として1つの Phase にまとめている。厳密に 1 モジュール 1 機能にする場合は、`phase5_editor.py` を「編集のみ」とし、ファクトチェックを `phase5_factcheck.py` などに分離する選択肢もある。現状は呼び出し元（pipeline）が単純になるよう、1 Phase にまとめている。

## 3. 各Phaseの詳細

### Phase 0: Persona Lock（ペルソナ固定）

**目的**: 記事全体で一貫した「人格」を維持する

#### 3.0.1 一人称の固定
| 視点タイプ | 一人称 | 使用場面 |
|-----------|--------|----------|
| 個人ブロガー | 僕 | 体験談、考察 |
| 専門家 | 私 | 解説、教育 |
| 企業 | 私たち / 当社 | サービス紹介、広報 |
| 友人 | わたし | カジュアル、親密 |

#### 3.0.2 口癖の設定
記事全体で2〜3個の「個人フレーズ」を繰り返し使用し、人格の一貫性を演出。

**例**:
- 「正直なところ」「実感として」（内省型）
- 「面白いのは」「驚いたのは」（発見型）
- 「ポイントは」「大事なのは」（教育型）

---

### Phase 1: Empathy（共感注入）

**目的**: 「この人、わかってる」と感じさせる

#### 3.1.1 心理学的根拠
- **感情心理学**: 自己開示は信頼と親近感を生む
- **ミラーニューロン理論**: 他者の感情を言語化されると共感が生まれる

#### 3.1.2 実装要素

| 要素 | 説明 | 例文 |
|------|------|------|
| 脆弱性の開示 | 冒頭で弱さ・失敗を見せる | 「正直、僕も最初は失敗した」 |
| 感情ミラーリング | 読者の想定感情を言語化 | 「イラッとしますよね」 |
| 直接呼びかけ | 読者を巻き込む問いかけ | 「経験ありませんか？」 |

#### 3.1.3 検出マーカー
```
vulnerability: 失敗, 間違, 恥ずかし, 不安, 迷, 悩
mirror: ですよね, ありますよね, わかります
self_disclosure: 正直, 実は, 本音, 告白すると
```

---

### Phase 2: Curiosity（興味設計）

**目的**: 「続きが読みたい」と感じさせる

#### 3.2.1 心理学的根拠
- **情報ギャップ理論**（Loewenstein, 1994）: 知っていることと知りたいことの差が好奇心を生む
- **ツァイガルニク効果**: 未完了のタスクは記憶に残りやすい

#### 3.2.2 実装要素

| 技法 | 説明 | 例 |
|------|------|-----|
| 情報の小出し | 結論を匂わせつつ詳細は後で | 「理由は3つある。まず...」 |
| パターン破壊 | 予想を裏切る展開 | 「でも、実は逆だった」 |
| オープンループ | 伏線を張り回収を遅らせる | 「後で詳しく話すけど...」 |
| 緊張と解放 | 問題→不安→解決の波 | 不安を煽ってから希望を示す |

#### 3.2.3 構造パターン
```
導入: 常識の提示 → 否定 → 新しい視点の予告
展開: 情報を段階的に開示（全部言わない）
結び: 回収 + 次への期待
```

---

### Phase 3: Humanity（人間味付与）

**目的**: 「機械が書いたものではない」と感じさせる

#### 3.3.1 心理学的根拠
- **心理言語学**: 人間の発話には「言い直し」「脱線」が自然に含まれる
- **認知負荷理論**: 完璧すぎる文章は逆に不自然

#### 3.3.2 実装要素

| 要素 | 説明 | 例 |
|------|------|-----|
| 脱線と回帰 | 話が逸れて戻る | 「ちなみに〜。話を戻すと」 |
| 言い直し | 自己訂正 | 「というか」「いや、正確には」 |
| 不完全性 | 曖昧さを残す | 「たぶん」「うまく言えないけど」 |
| レジスター混在 | 丁寧語にカジュアルを混ぜる | 「〜なんですよね」 |

#### 3.3.3 検出マーカー
```
digression: ちなみに, 余談ですが, 話が逸れますが
self_correction: というか, いや, 正確には, 言い換えると
uncertainty: たぶん, だと思う, かもしれない
casual_break: なんですよね, じゃないですか, まあ
```

---

### Phase 4: Rhythm（リズム調整）

**目的**: 読みやすく、息継ぎのあるテンポを作る

#### 3.4.1 理論的根拠
- **散文リズム論**: 短文と長文の交互配置が読みやすさを生む
- **認知負荷**: 均一な文長は処理負荷を上げる

#### 3.4.2 実装要素

| 要素 | 目標値 |
|------|--------|
| 短文 | 20〜40文字（強調・余韻） |
| 中文 | 50〜70文字（説明・展開） |
| 長文 | 80〜100文字（複雑な論理） |
| 配置 | 短→中→長→短のような波 |

#### 3.4.3 段落の呼吸
- 3〜5文で1段落
- 段落間に「読者が息継ぎできる」余白
- 強調したい1文は独立段落に

---

### Phase 5: Editor（編集者校正 + ファクトチェック）

**目的**: 品質保証と事実確認

#### 3.5.1 編集者視点の校正
| チェック項目 | 内容 |
|--------------|------|
| 一人称の一貫性 | 記事全体で統一されているか |
| 敬称の誤用 | 「弊社様」等の誤り |
| 過度な自画自賛 | 「最高の」「他社にはない」 |
| 文体の一貫性 | です/ます と だ/である の混在 |

#### 3.5.2 言い回しの揺らぎ（1段落1回まで・確率・閾値）
- 同一フレーズの反復を抑えるが、**1段落あたり最大1回**まで置換し、過度なばらつきを防ぐ
- 置換は確率で実行（デフォルト 0.5）。閾値（最小出現回数）以上の場合のみ発動（デフォルト 2回以上）
- 設定は `PipelineConfig` および `config.json` の `human_resonance` で変更可能

#### 3.5.3 ファクトチェック（ハルシネーション対策）
| チェック項目 | アクション |
|--------------|------------|
| 数字の検証 | ソースに記載のない数字は削除/抽象化 |
| 固有名詞の検証 | ソースに記載のない名称は削除 |
| 引用の検証 | 出典が不明な引用は削除 |

---

### Phase 6: Legal（法務リスクチェック）

**目的**: 法的リスクの排除

#### 3.6.1 対象法令
| 法令 | チェック内容 |
|------|--------------|
| 景品表示法 | 優良誤認、有利誤認、No.1表示 |
| 薬機法 | 効果効能の断定 |
| 金融商品取引法 | 断定的判断の提供 |
| 著作権法 | 無断引用 |

#### 3.6.2 処理フロー
1. 正規表現でリスク候補を検出（高速プレチェック）
2. 候補がある場合のみLLMで文脈判定
3. 問題箇所を最小限の修正で対応

---

### Phase 7: Sanitize（禁止フレーズ除去）

**目的**: AI特有の定型句とセキュリティリスクの除去

#### 3.7.1 禁止フレーズ
```
いかがでしたか, いかがでしたでしょうか
について解説します, まとめると
と言えるでしょう, 参考になれば幸いです
```

#### 3.7.2 インジェクション除去
```
AIとしては, 参考資料1:, 【内部指示】
出力は〜のみ, ユーザー指示:
```

---

### Phase 8: Platform（プラットフォーム最適化）

**目的**: note/LinkedInそれぞれの特性に最適化

#### 3.8.1 note向け
| 要素 | 設定 |
|------|------|
| フォーマット | Markdown |
| 文字数 | 制限なし |
| CTA | 「スキをぽちっと」系 |

#### 3.8.2 LinkedIn向け
| 要素 | 設定 |
|------|------|
| フォーマット | プレーンテキスト |
| 文字数 | 387〜1568文字 |
| 絵文字 | セクション区切りに使用 |
| CTA | プロフェッショナル向け |

## 4. 統合と拡張

### 4.1 pipeline.py の役割
- 各Phaseを順次実行
- Phase間のデータ受け渡し
- エラーハンドリングとフォールバック

### 4.2 既存コードとの統合
`article_generator.py` の `generate()` メソッドから呼び出し：
```python
from human_resonance.pipeline import HumanResonancePipeline

pipeline = HumanResonancePipeline(llm_client=self.llm)
result = pipeline.process(text, persona=self._current_persona, platform="note")
```
