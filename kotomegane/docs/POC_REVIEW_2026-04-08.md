# Kotomegane (コトメガネ) PoC レビュー

**作成日**: 2026-04-08  
**対象バージョン**: PoC (2026-04-05 スナップショット時点)  
**レビュー観点**: 機能完成度・アーキテクチャ品質・一般的なLLMOとしての充足度

---

## 1. ソフトウェア概要

**Kotomegane** は、ビジネスキーワードに対するLLM（大規模言語モデル）の回答内に自社ドメイン・ブランドがどの程度露出しているかを計測・可視化するLLMO（LLM Operations）ツールである。

### 主要機能

| 機能 | 説明 |
|---|---|
| マルチプロバイダー対応 | OpenAI / Gemini / Claude の3社切り替え |
| 可視性スコアリング | LLMスコア + 決定論的スコアの2軸評価 |
| クエリ計画・展開 | 1質問 → 最大5展開、日本語短縮処理 |
| 実行モード | 手動・バッチ・スケジューリングの3モード |
| 引用追跡 | ドメイン別引用状況・引用シェア計算 |
| コスト管理 | バジェットガードレール・プロンプトキャッシュ最適化 |
| ダッシュボード | KPI表示・トレンド・エクスポート |

## 2. 良い点

### 2-1. アーキテクチャ設計

- **マルチプロバイダー抽象化**が `Protocol` ベースで実装されており、新プロバイダーの追加が容易
- **Factory パターン**によるプロバイダー切り替えが疎結合で Clean
- `analysis_core/` と `llmo_core/` の分離により、分析ロジックとLLM通信が独立して変更可能
- レイヤー構成（UI / ビジネスロジック / LLMクライアント / ストレージ）が明確

### 2-2. スコアリングの堅牢性

LLMスコア（モデルが返す0-100値）と決定論的スコア（ルールベース計算）の2軸を採用しており、LLMの回答揺れに対して安定した指標を提供できる点は差別化要素として有効。

**決定論的スコアの構成要素:**

| 要素 | 加点/減点 |
|---|---|
| ターゲットドメインヒット | +40pt |
| ブランドメンション | +15pt |
| 自社引用（1件あたり） | +12pt |
| 引用シェア率 | +15pt |
| 競合ペナルティ | -12pt |
| 外部のみペナルティ | -18pt |

### 2-3. コスト管理

- プロンプトキャッシュ戦略（同一プレフィックスで複数クエリ実行）により、OpenAIで最大10倍のコスト削減
- 日次上限・実行上限のバジェットガードレールが実装済み
- 推定コスト計算・JPY換算まで含めた透明性の高いコスト表示

### 2-4. 自動化・運用性

- スケジューラが60秒ごとにDB監視し、期日到来したバッチジョブを自動発火
- Batch API活用による非同期大量処理（コスト・レート制限の両面で有利）
- プロンプトキャッシュ最大化のため実行順序を固定する設計が適切

### 2-5. セキュリティ配慮

- 検索結果経由のプロンプトインジェクション対策がシステムプロンプトに明記
- 信頼されていない入力のハンドリングが意識されている

## 3. 問題点・改善が必要な部分

### 3-1. 致命的な問題

#### テストが存在しない

手動確認と `py_compile` による構文チェックのみで、自動テストがゼロ。

**リスク:**
- `deterministic_scoring.py` のロジック変更時に回帰が検出できない
- プロンプト変更がスコアに与える影響を定量的に把握できない
- リファクタリングの安全網がない

**改善案:**
```
tests/
├── test_deterministic_scoring.py   # スコア計算ロジックの単体テスト
├── test_metrics.py                 # KPI集計の単体テスト
├── fixtures/
│   └── mock_llm_responses.json     # モックAPIレスポンス
└── test_storage.py                 # DB読み書きの統合テスト
```

#### プロンプトのハードコード

`prompts.py` に日本語前提のシステムプロンプトがベタ書きされており、スコアリングルールがプロンプトとコードに分散している。

**問題:**
- 英語市場・多言語展開が困難
- プロンプト変更がコードデプロイと連動してしまう

**改善案:**
- プロンプトをYAML/JSONで外部化し、言語・用途ごとにテンプレート管理
- バージョン番号をDBに保存し、スコアとプロンプトバージョンを紐付け

---

### 3-2. 機能面の問題

#### 決定論的スコアの重み付けが固定値

業種・サービス特性によって「ドメインヒットの重要度」は大きく異なるが、現状は全顧客に同一ウェイトが適用される。

**改善案:** 管理画面でウェイトをスライダー調整可能にし、変更履歴をDBに保存

#### SQLiteのスケーラビリティ限界

スケジューラ（バックグラウンド）とUI（フォアグラウンド）が同時にDBへ書き込む構成のため、WALモードの有効化が必須。SaaS化時はPostgresへの移行が必要。

**確認事項:**
```python
# storage.py にて以下が設定されているか確認
conn.execute("PRAGMA journal_mode=WAL")
```

#### エラーハンドリングの一貫性不足

JSON truncation recovery は実装されているが、一部のAPIエラーが無言で握りつぶされる可能性がある。バッチジョブ失敗時のリトライ戦略が明確でない。

**改善案:**
- 失敗したバッチアイテムを `failed_batch_items` テーブルに記録
- 指数バックオフによる自動リトライ（最大3回）

#### APIキー管理

`.env` ファイルによる単一APIキー管理のため、マルチユーザー環境で全ユーザーが同一キーを共有する構造になっている。

**改善案:**
- ユーザーごとのAPIキー入力・暗号化保存
- 将来的にはAWS Secrets Manager / Azure Key Vault 連携

## 6. 総評

### 強み

PoC としての完成度は高い。スコアリング2軸（LLM + 決定論的）・マルチプロバイダー・コスト管理・スケジューリングの組み合わせは、競合ツールに対する明確な差別化要素として機能する。特にプロンプトキャッシュ戦略とバジェットガードレールの組み合わせは、エンタープライズ顧客への訴求ポイントになりうる。

### 最重要課題

**「プロンプト変更とスコア変動の因果追跡」が欠如している**ことは、LLMOツールとして本質的な問題である。顧客が「コンテンツを改善した結果スコアが上がったのか、プロンプトが変わったからなのか」を判断できなければ、ツールへの信頼性が損なわれる。

### SaaS化に向けた優先事項

1. テストインフラの整備（信頼性の基盤）
2. プロンプトバージョン管理（説明可能性の確保）
3. アラート機能（顧客の継続利用に直結）

これら3点に投資することで、PoC から顧客に提供可能なプロダクトへの移行が現実的になる。
