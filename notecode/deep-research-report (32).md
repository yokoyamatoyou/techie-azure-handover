## 結論

最も有望なのは、**DとEを前処理層、Cを生成層として組み合わせる方式**です。言い換えると、**「情報抽出と文体生成を分離」し、さらに「二層圧縮で素材を整理」したうえで、本文は基本的に一発生成し、その後で後半重点の編集と必要最小限の部分再生成を行う**構成が、いまの日本語ブログ用途には最も筋がよい、というのが今回の結論です。これは、古い長文生成研究ではアウトライン分割や再帰的再プロンプトが有効だった一方、最新の entity["company","OpenAI","ai company"] のGPT-5系ガイドでは「短く outcome-first な指示」「legacy prompt stack の持ち込み回避」「必要な失敗モードにだけブロック追加」が推奨され、GPT-5.4系では長い回答でも人格・トーンのドリフトが減っていると明示されているためです。加えて、近年の研究では**計画は有効でも、それを推論時に露出した多段階プロンプトにする必要はなく、単一ターン生成の中に内在化したほうがよい**ことも示されています。citeturn3view0turn2view4turn24view0turn30search0turn21search7

したがって、**2000字前後の日本語ブログ**という条件では、**骨格作成 → セクション分割生成 → 統合**をデフォルトに据えるべきではありません。これは捨ててよい、というより、**主役から降格させるべき**です。具体的には、分割生成を使うのは、**3000字級以上で構造拘束が強い記事**、**法務・制度・仕様など見出し単位のカバレッジ保証が優先される記事**、**小型モデルのみで厳密な手順制御が必要な場合**に限るのが妥当です。古い研究で分割生成が効いたのは、長距離一貫性が弱いモデル・数千語級の物語・長文記事を対象にしていたからであり、Re3やDOCはその文脈で有効でした。しかし、それらは**創作寄りの数千語長文**に対する知見で、**2000字前後の日本語企業ブログにそのまま輸入すると過剰制約になる**可能性が高いです。citeturn21search2turn21search4turn21search1turn24view0turn3view0

一方で、**「一発生成 → 編集 → 部分再生成」**は、以下の条件で特に強くなります。**記事長が中程度**、**文体の統一感が重要**、**URL情報が事前に素材化されている**、**ブランドや社風に合うトーンが重要**、**後半の一般論化だけを局所修正したい**、この五つが揃うときです。近年のSelf-Refine系研究は、初稿のあとにフィードバックと修正を回すこと自体が有効であると示しており、OpenAIの最新ガイドも、長い工程指示より**明確な成功条件・制約・短い人格指定**を勧めています。つまり、最初の文章は**1本の連続したデコードで作って流れを確保し**、その後に**編集者的視点で削る**ほうが、セクション分割で最初から細切れに作るより自然さが残りやすい、という理解が現在の知見に合います。citeturn25search0turn25search6turn2view2turn3view1turn24view0

URL圧縮については、**記事タイプ別に変えるべき**です。これは今回の調査の中でもかなり確信度が高い部分です。Decision-Focused Summarization は「意思決定に無関係な情報をまとめに混ぜてしまう」問題を指摘し、QMSumやGraphRAGは**単一の汎用要約ではなく、問いや目的に合わせて関連情報を再構成する必要**を示しています。さらに、可読性制御要約やMixed-attribute controllable summarizationの研究は、**読者・目的・特性の混合制御**が必要であり、粗いcontrol tagでは不十分だと述べています。つまり、会社案内、採用、導入事例、専門知識、お知らせを同じ「URL要約器」で処理すると、品質が平板化するのは自然です。citeturn15view0turn15view2turn28view1turn28view2turn28view0turn14view3

生成ペルソナ、編集ペルソナ、再生成ペルソナを分ける設計は、**実務的には強く推奨**できますが、**直接この三分離を検証した公開研究はまだ薄い**、というのが正確な言い方です。ただし、人格指定が効くとする最新GPT系の公式ガイド、persona-aware summarization の研究、critique-and-refine 系研究を合わせて読むと、**「書く役割」と「直す役割」と「局所修復する役割」は分けたほうが制御しやすい**という判断は妥当です。とくに日本語ブログでは、編集工程が**語尾・助詞・段落リズム・抽象語過多**を抑えるうえで強い意味を持ちます。citeturn2view2turn2view7turn14view0turn25search0

日本語特性については、**主因ではなく増幅因子**とみるのが妥当です。ゼロ照応、主語省略、話題優先、係り受け、文末表現、機能語と句読点のスタイル性は、確かに分割生成の不自然さを増幅します。しかし、根本原因はおそらく**複数回生成による文脈断絶、位置バイアス、局所最適化、後工程の統合不足**です。長文文脈研究では、関連情報が文脈の中ほどにあると取りこぼしやすく、モデルは「知っていても出せない」ことがあり、やりとりが長くなると指示安定性も落ちます。日本語はもともと前文脈に寄りかかる言語なので、その断絶が英語より目立ちやすい、という位置づけです。citeturn6view0turn6view1turn6view4turn7view0turn19search14turn19search1turn19search9

## 原因分析

### オーケストレーションの問題

いま起きている失敗のかなりの部分は、モデル性能そのものより、**生成を分割しすぎていること**で説明できます。Lost in the Middle は、長文コンテキストモデルでも関連情報が**先頭や末尾に置かれたときに最も使われやすく、中ほどでは大きく性能が落ちる**ことを示しました。Google Research の follow-up でも、これは単なる偶然ではなく、**U字型の注意バイアス**に関係すると説明されています。もし各セクション生成のたびに、同じ圧縮要約や指示群を何度も渡しているなら、毎回モデルは**目立つ要約点を再選択**しやすくなり、意味重複と言い換え重複が増えます。citeturn6view0turn6view1

さらに、長文失敗研究では、モデルは関連情報の位置を内部的には捉えていても、実際の出力でそれをうまく使えない「know but don’t tell」現象が報告されています。加えて、指示安定性研究は、会話が長くなると**注意減衰により指示ドリフト**が起きることを示しました。これをブログ生成に引き寄せると、セクションごとの独立生成は、毎回新しいローカル文脈で**その場しのぎの最適化**を起こしやすく、統合時にはすでに全体の温度感が崩れている、という構造になります。citeturn6view4turn7view0turn9view0

この観点では、あなたが観察した「まとめ感が強い」「URL情報が平板な要約として並ぶ」「後半ほどAIっぽい」は、かなり整合的です。Chromaのcontext rotレポートや entity["company","Anthropic","ai company"] のcontext engineering記事は、**トークンを増やせば増やすほど良くなるわけではなく、むしろ注意資源が薄まる**と明言しています。これは、URL要約・ガイドライン・骨格・直前文脈を全部詰め込むほど、モデルが高信号と低信号を見分けにくくなることを意味します。分割生成は「一回あたりの長さ」を減らしているようでいて、実際には**高信号な素材の選別を繰り返し失敗させる**ことがあります。citeturn7view3turn7view4turn22view0

### 日本語特性の問題

日本語では、**主語や目的語の省略**、**話題と叙述の連鎖**、**文末表現の選択**が、段落またぎの自然さに強く関わります。日本語のゼロ照応研究は、**省略された必須格が先行文脈に依存して復元される**ことを前提にしていますし、日本語の談話一貫性研究では**共参照の使い方がコヒーレンス評価に有効**だとされています。つまり、前段落で設定した主体や話題の流れが切れると、英語以上に「誰が／何が」のつながりが痩せやすいのです。citeturn19search14turn19search9

また、日本語LMのtopic-comment構造の研究は、**文脈に関連する情報を文頭側へ置く**ような人間の談話選好をLMがどこまで再現できるかを問題にしています。分割生成では、その章だけを局所的にもっともらしく書けても、記事全体を通じた**話題提示→展開→回収**の流れが失われやすくなります。これは、ユーザーが感じる「前後の論理がつながらない」「後半になるほど一般論化する」に直結します。citeturn19search1

日本語のAIっぽさについては、 stylometry 研究がかなり参考になります。日本語では、**品詞bigram、助詞bigram、読点位置、機能語率**でAI文と人間文が高精度に分離でき、2025年の追試でも、**語尾・接続・句読点・言い回し**が判断材料になっていることが報告されています。重要なのは、ここで差が出ているのが「禁止語」だけではなく、**機能語・終止・間の取り方・句読点・句パターン**だという点です。したがって、「第一歩」「効く」を禁じても効果が浅い、というあなたの観察は、研究上も整合的です。citeturn18view1turn18view2

トークナイゼーションは副次要因です。日本語では形態素境界が自明でなく、SentencePieceのようなサブワード分割が広く使われています。人間にとって読みやすい分割と、モデルにとって扱いやすい分割は必ずしも一致しないという研究もあります。とはいえ、**2000字ブログの不自然さの主因がトークナイザとは言いにくい**です。影響はありますが、優先順位としては**圧縮・オーケストレーション・編集設計**のほうが上です。citeturn20search2turn20search0turn20search1

### モデルサイズとプロンプト追従性の問題

GPT-5.4系の公式ガイドでは、**大きいモデルは長い回答でもトーン維持が相対的に強く、miniはより文字どおりで、暗黙の補完が弱い**と整理されています。これは、miniで「厳密な実行手順」「重要ルールを先頭」「曖昧時の振る舞いを明示」が必要になる一方、最終的な日本語の肌理や読後感では大きいモデルが有利になりやすいことを意味します。言い換えると、**miniに多段階オーケストレーションを背負わせるほど自然さが削れやすい**ものの、**素材抽出や分類のような閉じたタスクにはminiが向く**、という切り分けです。citeturn3view0turn24view0

最新のOpenAIドキュメントは、GPT-5系全体について**結果を明確に定義し、詳細すぎる工程誘導は減らし、成功条件と停止条件を明示する**方向を勧めています。さらに reasoning best practices では、**chain-of-thought を出力させるようなプロンプトは不要**で、簡潔で直接的な指示のほうがよいとされています。これは、古いLLM時代の「とにかく細かい工程を全部書く」設計が、そのまま現行モデルの最終文体にも良いとは限らないことを示します。citeturn24view0turn30search0turn30search3

### URL情報圧縮の問題

ここは非常に重要です。QMSum は、**単一の短い要約では多様な利用者の欲しい情報を満たせない**ことを前提に、query-based summarization を定義しました。Decision-Focused Summarization は、**テキストだけ見て関連度を決めると意思決定に不要な情報が混ざる**と指摘しています。GraphRAG も、グローバルな質問は通常のretrieve-and-answerではなく、**query-focused summarization の問題**だと述べています。つまり、URL圧縮を「何でも短くすればよい」と考えると、生成に入る前にすでに負けています。citeturn28view1turn15view0turn28view2

さらに、readability controllable summarization の最新研究は、粗い prefix tag より、**読者要求をQAペアとして明示するほうが細粒度制御に効く**と報告しています。MACSum も、Length・Specificity・Topic・Speaker などの**混合属性制御**が必要だと示しています。あなたの用途に引きつけると、URL圧縮は「要約」ではなく、**記事タイプと想定読者に対する素材化**であるべきです。ここでやるべき仕事は、圧縮率を上げることではなく、**本文に使うべき事実・背景・にじませる要素・後半で回収する要素・書いてよい範囲・書いてはいけない推測**を分けることです。citeturn28view0turn14view3turn14view0

### 古い知見を最新モデルへ適用している問題

古いLLM時代にアウトライン生成や分割生成が推奨された理由は明確です。より短いコンテキスト、弱い長距離一貫性、数千語級生成での破綻回避、RAG統合能力の不足があったからです。そのため、Re3やDOCのような**計画→分割→修正**は合理的でした。citeturn21search2turn21search4

しかし、最新GPT系では、OpenAI自身が**legacy prompt stack をそのまま持ち込むな**と書いています。GPT-5.5では outcome-first prompts が効きやすく、GPT-5.4でも「最小のプロンプトから始めて、測定された失敗モードにだけブロックを足す」ことが推奨されています。したがって、**過去の“安全策”が、最新モデルではノイズ・機械的口調・過剰拘束になっている**というあなたの疑いは、かなり妥当です。citeturn2view3turn3view0turn24view0

## 推奨アーキテクチャ

### 古いLLM向け設計

古いLLM向けの推奨設計は、次のように整理できます。**長文一発生成が破綻しやすい、長距離依存が弱い、長いRAG文脈を使いきれない**条件では、**アウトライン、分割生成、再帰的リプロンプト、可視的な中間推論**は合理的でした。Re3やDOCが有効だったのも、この文脈です。これらの知見は「間違いだった」のではなく、**当時の制約に対する正しい工学**でした。citeturn21search2turn21search4turn6view0

### 最新GPT系向け設計

最新GPT系、とくに GPT-5.4/5.5 では、**2000字前後のブログ**なら、まず**一発生成をデフォルト**に置くべきです。ここで重要なのは、**一発生成だから雑でよい**ではなく、**前段の素材設計を強くし、本文生成時の工程指示は減らす**ことです。要件は、短い人格、明確なゴール、成功条件、禁止構造、必須事実、避ける推測、文量、最後の着地点だけに絞ります。工程はモデルに選ばせ、必要なら後から編集します。citeturn24view0turn30search0turn2view2

### 推奨パイプライン

以下が、今回の用途に対する**推奨パイプライン**です。

1. **URL取得と正規化**  
   HTML本文、見出し、表、箇条書き、固有名詞、数値、日付、引用候補、CTA要素を抽出し、ナビゲーションや重複フッタを除去します。ここでは「読みやすい要約」をまだ作りません。作るのは**事実オブジェクト**です。根拠は、長文文脈での位置バイアスと、query/decision/persona-aware summarization の必要性です。citeturn6view0turn28view2turn15view0turn14view0

2. **URLごとの事実抽出**  
   各URLから、`claim_id / fact_text / evidence_span / source_url / confidence / fact_type / tone_signal / claim_boundary` をJSONで抽出します。`fact_type` は、数字、沿革、制度、価値観、場面描写、読者便益、禁止推測などに分けます。**最初から prose summary にしない**ことが重要です。citeturn24view0turn30search8

3. **複数URL横断の重複排除**  
   claim_id 同士を意味クラスタリングし、同一主張の言い換え群をまとめます。ここで「どのURLに何回も出るか」を強さの指標にできますが、本文には**最も具体的な1本**だけを使うようにします。これで、あとから各段落で同じ主張を別表現で繰り返す事故を減らせます。これは研究の直接写しではなく実装提案ですが、query-focused summarization と decision-focused summarization の発想に一致します。citeturn15view0turn28view2

4. **記事タイプ別素材化**  
   ここがE方式の中心です。クラスタ化した事実を、記事タイプごとに  
   `must_use / optional_background / implicit_style / explicit_mentions / later_recall / avoid_expression / hard_facts / no_inference / audience_questions`  
   に振り分けます。**本文に使う情報**と**文体にだけ効かせる情報**を分けることが重要です。単なる要約ではなく、**素材メモ**にします。readability controllable summarization と mixed-attribute control の知見は、この方向を明確に支持します。citeturn28view0turn14view3turn14view0

5. **生成ペルソナ選択**  
   ペルソナは短くします。最新のOpenAIガイドは、人格もコラボレーションスタイルも**短く保て**としています。ここでのペルソナは、ロールプレイ的な飾りではなく、**視点・距離感・具体性の選び方**を規定するものです。citeturn2view2turn2view4

6. **一発生成**  
   2000字前後の記事は、**原則1回の連続生成**で書きます。必要なら内部用のごく短い hidden plan は作ってもよいですが、**見出しごとの本文生成には分解しない**のが基本です。ここで守るべきなのは、必須事実、禁止推測、段落数の目安、文体仕様、最後の着地仕様だけです。GPT-5系は結果仕様に強く、過程の過密指定は逆効果になりやすいです。citeturn24view0turn3view1turn30search0

7. **後半劣化チェック**  
   生成後、**後半35〜45%**を重点検査します。検査対象は、抽象語率、意味重複、語尾単調、一般論化、根拠のない読者配慮、汎用結論です。長文文脈研究と length-following 研究は、長くなるほど指示や制約の維持が難しくなる傾向を示しており、OpenAI cookbook でも長いやりとりではマークダウン指示の劣化が見られるとしています。したがって、後半重点の設計は合理的です。citeturn9view1turn2view5turn7view0

8. **編集ペルソナによる検査と最小修正**  
   編集ペルソナは、記事全体を壊さず、**重複削除・抽象語削減・リズム調整・結論の尖らせ**を行います。ここでは新事実を足さず、意味を薄めないことが制約です。Self-Refine系は、この「初稿→批評→改善」が有効な一般戦略であることを示しています。citeturn25search0turn25search6

9. **必要箇所のみ部分再生成**  
   編集で直らない場所だけ、**左アンカー1文＋対象スパン＋右アンカー1文**を渡して、120〜300字程度を局所再生成します。大量の再生成は再び文体を壊すので避けます。再生成ペルソナは「接続と密度の修復」に限定します。これは研究の直接結果というより、上の知見から導く実装上の最適化です。citeturn25search0turn24view0

10. **最終検査**  
    hard facts の被覆、unsupported claim、claim_id重複使用、段落長ばらつき、語尾多様性、ペルソナ維持率を確認して確定します。**アウトラインはここではじめて coverage checker として使う**のがよいです。本文生成の器ではなく、欠落検査の器にします。citeturn24view0turn10view0

要するに、**A方式をC方式で置き換える**のではなく、**Aの“骨格”を生成の主経路から外し、D/Eで素材を強くし、Cで書いて、編集と局所再生成で整える**のが推奨です。

## 記事タイプ別の圧縮テンプレート

以下は、研究で示された **query-/decision-/persona-/reader-demand-aware summarization** の考え方を、日本語ブログ生成向けに実装へ落としたテンプレートです。共通フィールドは次のとおりです。  
`must_use_facts / optional_background / implicit_style / explicit_mentions / later_recall / avoid_claims / hard_facts / no_inference / audience_questions / evidence_priority` 。前半に置くのは `must_use_facts`、末尾に再配置するのは `later_recall` です。これは位置バイアス対策としても有効です。citeturn28view2turn15view0turn28view0

**会社案内**  
- 残す: 創業背景、事業領域、対応地域、主要顧客層、運営年数、代表的な取り組み、数字で示せる信頼材料。  
- 捨てる: 抽象スローガンの反復、沿革の細部、一般的な理念文の重複。  
- 本文に明示: 何をしている会社か、誰にどう役立つか、どの現場で強いか、信頼の根拠。  
- 文体に反映: 落ち着き、誠実、言い過ぎない自信。  
- 後半で回収: 価値観が具体的取り組みにどう出ているか。  

**商品ブランディング**  
- 残す: 商品特徴、開発背景、使用シーン、悩み、差別化点、使用後の変化、言い過ぎNG表現。  
- 捨てる: カタログ的列挙、競合比較の断定、スペックのみの平板羅列。  
- 本文に明示: どの場面で効くのかではなく、**どの不便がどう変わるのか**。  
- 文体に反映: 使用感、温度、軽い情緒、過剰販促の抑制。  
- 後半で回収: 開発意図と利用シーンの接続。  

**サービス紹介**  
- 残す: 対象読者、導入導線、提供範囲、差別化、対応フロー、リスクや不向き条件。  
- 捨てる: 実態のない「伴走」「最適化」などの抽象持ち上げ。  
- 本文に明示: 誰向けか、導入前に何が分かるか、依頼後に何が起きるか。  
- 文体に反映: 明快さ、手触り、説明的だが営業臭を抑える。  
- 後半で回収: 読者が次に確認すべき具体事項。  

**日々の出来事**  
- 残す: 場面、行動、人の動き、季節、ちいさな発見、現場の音や手触り。  
- 捨てる: 学びの一般化、無理な教訓化、会社PRへの唐突な接続。  
- 本文に明示: その日の空気感、見えた変化、短い視点の揺れ。  
- 文体に反映: ささやかさ、余白、観察の具体性。  
- 後半で回収: 1つの小さな具体物や場面。  

**採用・社内文化**  
- 残す: 働く人の様子、会話の雰囲気、制度の使われ方、実例、候補者が気にする不安。  
- 捨てる: 美辞麗句、制度名の羅列、抽象的な文化語。  
- 本文に明示: 実際にどんなコミュニケーションがあり、何が安心材料か。  
- 文体に反映: 飾りすぎない透明感。  
- 後半で回収: 制度よりも「使われている場面」の一例。  

**専門知識記事**  
- 残す: 読者の誤解点、判断基準、手順、例外、注意点、断言範囲、具体例。  
- 捨てる: イントロの一般論、SEO的な薄い見出し反復。  
- 本文に明示: まず何を見ればよいか、どこで判断が分かれるか、何を誤解しやすいか。  
- 文体に反映: 明晰さ、限定付き断定、例示。  
- 後半で回収: 先に出した判断基準を再度具体例に接続。  

**導入事例**  
- 残す: 導入前課題、関係者、導入経緯、変化、数値、制約、成功しすぎない表現。  
- 捨てる: 成功談の誇張、原因不明の成果、汎用ベネフィットの丸い表現。  
- 本文に明示: 課題→意思決定→実装→変化の鎖。  
- 文体に反映: 他社でも起きうる現実味、誇張抑制。  
- 後半で回収: 導入前の躓きが何で、どう越えたか。  

**お知らせ**  
- 残す: 何が、いつから、誰に、どう変わるか、何をしてほしいか、例外。  
- 捨てる: 余分な背景、感情的装飾、長い前置き。  
- 本文に明示: 変更点と行動。  
- 文体に反映: 短さ、誤解回避。  
- 後半で回収: 再確認すべき日付・対象・手続き。  

このテンプレートで重要なのは、**「本文に明示する情報」と「文体にだけ反映する情報」を分けること**です。たとえば会社案内で価値観を全部明示すると理念の羅列になりますが、文体にだけ反映すれば押しつけがましさを避けられます。逆に、お知らせでそれをやると必要情報が欠けるので、明示優先になります。

## 記事タイプ別のペルソナ設計

最新のOpenAIガイドは、**人格指定は明確に、しかし短く**、協働スタイルと役割を分けるよう勧めています。したがって、ペルソナは長い性格設定ではなく、**責務・判断基準・禁止事項**の3点で設計するのがよいです。citeturn2view2turn2view4turn2view7

共通ルールは次の四つです。  
- 生成・編集・再生成の全員が**同じ hard_facts と no_inference 制約**を共有する。  
- 編集者は**新事実を追加しない**。  
- 再生成者は**対象スパン外を原則変えない**。  
- 3者とも**同じ target_reader と article_promise** を共有する。  

**会社案内**  
- 生成ペルソナ: 「現場の実態を知る企業紹介編集者」。誠実、具体、自己陶酔しない。  
- 編集ペルソナ: 「信頼性監修デスク」。理念の言い過ぎ、重複、空疎表現を削る。  
- 再生成ペルソナ: 「接続修復ライター」。前後の論理と温度感を合わせる。  

**商品ブランディング**  
- 生成ペルソナ: 「販促より使用感を描くブランドライター」。  
- 編集ペルソナ: 「誇張表現チェッカー」。効能誇張、競合断定、ふわっとした褒めを削る。  
- 再生成ペルソナ: 「情景補筆ライター」。使う場面の具体さを足し、セールス臭を抑える。  

**サービス紹介**  
- 生成ペルソナ: 「導入前の不安をほどく説明ライター」。  
- 編集ペルソナ: 「営業臭抑制エディタ」。抽象便益の連打を削り、フローを明快にする。  
- 再生成ペルソナ: 「手続き明確化ライター」。行動導線だけを書き直す。  

**日々の出来事**  
- 生成ペルソナ: 「観察を言葉にする社内日記ライター」。  
- 編集ペルソナ: 「教訓化防止エディタ」。無理な学び、一般論化、PR化を消す。  
- 再生成ペルソナ: 「場面描写補修ライター」。物・音・時間帯を足す。  

**採用・社内文化**  
- 生成ペルソナ: 「応募者の目線を知る文化編集者」。  
- 編集ペルソナ: 「盛りすぎ防止エディタ」。制度自慢の羅列とキラキラ語を削る。  
- 再生成ペルソナ: 「実例補強ライター」。働く場面や会話を局所的に補う。  

**専門知識記事**  
- 生成ペルソナ: 「誤解を先回りして解く実務解説者」。  
- 編集ペルソナ: 「断言範囲監査役」。言い切り過ぎ、一般論、薄い例示を修正する。  
- 再生成ペルソナ: 「例示強化ライター」。抽象説明を具体例に置き換える。  

**導入事例**  
- 生成ペルソナ: 「課題と変化を現実的に描くケースライター」。  
- 編集ペルソナ: 「成果誇張抑制エディタ」。原因不明の成功、過大評価を削る。  
- 再生成ペルソナ: 「因果接続ライター」。課題→施策→変化の1区間を補正する。  

**お知らせ**  
- 生成ペルソナ: 「誤解なく伝える広報担当」。  
- 編集ペルソナ: 「曖昧表現排除エディタ」。対象・日付・手順の抜けを潰す。  
- 再生成ペルソナ: 「要件再記述ライター」。末尾の案内部分だけを短く正確にする。  

ここでのポイントは、**生成ペルソナは“作る人”であり、編集ペルソナは“守る人”、再生成ペルソナは“縫う人”**だということです。3者を別人格にする狙いは、演出ではなく**認知負荷の分離**です。とくに mini 系では、1つのプロンプトに「自然さ」「事実厳守」「ブランド調」「重複削除」「語尾調整」「局所接続修復」を全部載せると、かなり機械的になります。役割を分けたほうが制御しやすいです。citeturn3view0turn24view0turn25search0

## AIっぽさ除去の具体策

日本語のAIっぽさは、禁止語だけでは抑えきれません。PLOSの日本語stylometry研究では、AI文と人間文の差は、**機能語、助詞、句読点位置、品詞連接、句パターン**に現れています。したがって、対策も**構造**でかける必要があります。citeturn18view1turn18view2

### 禁止語リストの位置づけ

禁止語リストは**補助輪**としては使えます。  
- 第一歩  
- 効く  
- 大切です / 重要です  
- してみてください  
- 〜の一つです  
- まずは〜  
- 読者に寄り添う定型句  
- 何より〜  
- 〜を実現します  
- 〜に貢献します  

ただし、これは**主制御ではありません**。禁止語に置換が起きるだけだからです。禁止語は**検査工程の警告**として使い、生成工程では**構造的条件**を渡すほうが有効です。

### 禁止語に依存しない構造的抑制

以下を、編集ペルソナの評価基準として持たせます。これは実装提案です。

- **段落役割の分散**  
  各段落を「観察」「背景」「具体例」「制約」「含意」「案内」のどれかに分類し、同じ役割が3段落以上続かないようにします。  
- **主張あたりの具体情報連結**  
  主要主張の直後には、固有名詞・数値・場面・手順のどれかを必ず1つ接続させます。  
- **結論の回収条件**  
  最終段落は、前半で出た具体情報を1つ回収し、その具体に対する含意を書く。抽象的な人生訓・一般論・行動喚起だけで終わらせない。  
- **重複検出を語彙ではなく意味で行う**  
  段落間の埋め込み類似度、同一 claim_id の再登場、述語パターンの反復を検出する。  
- **語尾のエントロピー管理**  
  「です。」「ます。」「ました。」「でしょう。」の偏りを監視し、末尾表現の単調化を抑える。  
- **段落長のゆらぎ**  
  全段落が均等長になるのを避け、短い段落と中段落を混ぜる。  
- **抽象語率より具体名詞率を上げる**  
  抽象語だけではなく、会社名、地名、部署名、道具、時間帯、数値、手順語を増やす。  

### 改行制御

改行は「2〜4文ごと」の固定ではなく、**役割変化で切る**ようにします。  
- 観察 → 含意  
- 背景 → 具体例  
- 課題 → 変化  
- 変更内容 → 読者行動  

これにより、等間隔改行のAIっぽさが減ります。

### 文末制御

文末は、**断定・説明・限定・観察・余韻**を混ぜます。例としては、  
- です / ます  
- でした / ました  
- と言えます  
- 〜が見えてきます  
- 〜という場面もあります  
- 〜にとどまります  
- 〜だったのだと思います  
のように機能を分けて設計します。  
ただし、会話調に寄せすぎると別のAIっぽさが出るので、記事タイプで許容幅を変えます。

### 意味密度向上

意味密度は、**段落ごとの情報利得**で考えます。編集時に「この段落は前段落から何を新しく付与したか」をラベル化し、新規性が弱い段落は削るか統合します。導入事例なら「課題→施策→変化」、専門記事なら「誤解→判定基準→例外」、日々の記事なら「観察→細部→感触」のように、段落が増えるたびに観点が変わることを求めます。

### URL情報の自然な織り込み方

URLを自然に織り込むには、**URL単位で書かない**ことが重要です。  
- 悪い例: URL1の要約 → URL2の要約 → URL3の要約  
- 良い例: claim cluster 単位で再構成し、本文では1つの論点に対して最も具体的な根拠だけ採用する  

つまり、URLは本文の構成単位ではなく、**証拠の供給源**です。本文の段落単位は、記事の論点と読後感で決めるべきです。GraphRAGやdecision-focused summarizationは、この再構成の必要性を裏づけます。citeturn28view2turn15view0

### 後半の汎用結論を避ける方法

後半がAIっぽくなる最大要因は、**安全で generic な閉じ方に逃げる**ことです。これを防ぐには、最終段落に次の制約をかけます。  
- 前半の具体要素を最低1つ再登場させる  
- 新しい一般論は追加しない  
- 行動喚起を入れる場合も、対象読者・場面・条件を限定する  
- 「まずは」「第一歩」「大切です」で閉じない  
- 結論ではなく、**記事全体の焦点を1段具体へ戻す**  

これで「丸い結論」と「無難な着地」がかなり減ります。

## 実験計画と評価指標

長文研究では、単純な needle-in-a-haystack や perplexity だけでは長文能力を見誤るとされ、最新の長文学習研究でも**下流タスク評価が必要**だとされています。したがって、今回の実験も最終的には**人手評価を中心に、補助として自動評価**を置くべきです。citeturn10view0turn26search1turn26search2turn26search4

### 比較すべき方式

最低限、以下を比較します。  
- A: 骨格分割生成方式  
- B: 一発生成方式  
- C: 一発生成＋後半補正  
- D: 情報抽出と文体生成分離  
- E: 二層圧縮＋一発生成＋編集  

私の推奨は、**まず A vs C vs E を中心比較**し、その後に D を因数分解して効きを測ることです。Bはベースラインとして残し、Aとの差だけでなく、C/Eとの差を見るべきです。

### テスト設計

**記事ジャンル**は、最低でも次の8種を固定で回します。  
会社案内、商品ブランディング、サービス紹介、日々の出来事、採用・社内文化、専門知識記事、導入事例、お知らせ。  

**URL本数**は 1本、3本、5本以上。  
**文字数**は 1200字、2000字、3000字。  
**モデル**は GPT-5.4 mini、より大きいGPT系モデル、可能なら他社大モデル1種。OpenAI公式には、GPT-5.4-mini は小型ゆえにより明示的な構造化指示が必要で、GPT-5.4以上はスタイル維持が強いとありますから、ここは必ず比較する価値があります。citeturn3view0turn24view0

実務上は、いきなり全組合せを回すと大きいので、**二段階評価**が現実的です。  
- スクリーニング段階: 8ジャンル × 3URL条件 × 3文字数 × 3方式（A/C/E） × 2モデル × 2seed  
- 確証段階: スクリーニング上位2方式だけを、全ジャンル・全モデル・温度差で再検証  

### 自動評価指標

以下を推奨します。

- **AIっぽさ proxy**  
  日本語stylometryベースで、品詞bigram、助詞bigram、句読点位置、機能語率、語尾分布、段落長CV を人間コーパスと比較した距離。基盤の考え方は日本語stylometry研究に依拠できます。citeturn18view1turn18view2
- **意味密度**  
  段落ごとの新規 claim_id 数 / 総文数。  
- **具体性**  
  固有名詞・数値・場所・時間表現・具体動作語の密度。  
- **重複率**  
  非隣接段落間の埋め込み類似度、同一 claim_id 重複、Self-BLEU。  
- **文体一貫性**  
  前半/後半の stylometric distance。  
- **改行リズムの自然さ**  
  段落長CV、文数CV、役割遷移の偏り。  
- **文末表現多様性**  
  文末n-gramエントロピー。  
- **URL情報反映精度**  
  must_use_facts recall、hard_facts precision。  
- **事実誤認の少なさ**  
  source-supported claim ratio。必要なら QAFactEval / SummaC 系を補助に使う。citeturn26search2turn26search4turn26search6
- **RAG層評価**  
  取得したURL素材については、faithfulness / answer relevance / context precision を RAGAS 的に測る。citeturn26search3turn26search7
- **総合生成品質**  
  BARTScore を source-conditioned に使い、表現品質の補助指標とする。citeturn26search1

### 人手評価指標

人手評価は**A/Bのブラインド比較**を基本にします。7件法でもよいですが、実務では**どちらが良いか**を選ばせるほうが安定します。評価項目は次のとおりです。

- 日本語としての自然さ  
- AIっぽさの少なさ  
- 意味重複の少なさ  
- 具体性  
- 文体一貫性  
- 後半の失速の少なさ  
- 記事タイプとの適合度  
- URL情報の自然な織り込み  
- 読後感  
- 事実の信頼感  

評価者は、**日本語ネイティブかつ記事読者に近い属性**を優先し、少なくとも 3名、できれば 5名で回します。採用記事なら候補者視点、商品記事なら顧客視点、専門記事なら準専門家視点を含めるとよいです。

### 成功基準

成功基準は、少なくとも次の4つです。  
- Aに対して、C/Eが**自然さ・一貫性・重複率**で有意に改善する  
- must_use_facts recall が大きく落ちない  
- 後半劣化率が下がる  
- 人手評価で「人が書いた感じ」「その記事タイプらしさ」が上がる  

### 失敗時の切り分け

- **自然さ↑ / 事実反映↓**  
  圧縮が強すぎる。must_use の選定か later_recall の設計を見直す。  
- **事実反映↑ / 自然さ↓**  
  生成プロンプトが工程過密。素材メモが要約文になっている。  
- **前半良い / 後半だけ悪い**  
  後半補正不足。結論アンカーと後半編集を強化。  
- **全体にAIっぽい**  
  禁止語ではなく、段落役割・語尾・機能語・句読点・段落長CVを見る。  
- **URLが平板に並ぶ**  
  URL単位の圧縮をやめ、claim cluster 単位へ作り替える。

### AIっぽさ検査チェックリスト

- 同じ主張を別表現で2回以上言っていないか  
- 各段落に新情報があるか  
- 後半が一般論に逃げていないか  
- 具体名詞・数値・場面が十分あるか  
- 語尾が「です/ます」一辺倒になっていないか  
- 段落長が均等すぎないか  
- URLごとの要約列挙になっていないか  
- 記事タイプらしい焦点があるか  
- 読者配慮の定型句が多すぎないか  
- 結論が「まずは」「第一歩」「大切です」で終わっていないか  

### 比較実験チェックリスト

- article_type ごとに条件を固定しているか  
- URL本数を 1 / 3 / 5+ で分けたか  
- 文字数を 1200 / 2000 / 3000 で分けたか  
- モデル差を見たか  
- mini と大型で同じ素材パックを使ったか  
- one-shot と split で must_use を揃えたか  
- 後半補正の有無を分離したか  
- 人手評価をブラインドにしたか  
- 自動評価と人手評価の相関を見たか  
- failure mode を保存したか  

### 推奨パイプラインの要約

最終的な推奨は、次の一行に集約できます。  
**URL取得 → URLごとの事実抽出 → 横断重複排除 → 記事タイプ別素材化 → 生成ペルソナで一発生成 → 後半重点検査 → 編集ペルソナで最小修正 → 必要箇所のみ再生成 → 最終検査**。  
骨格は**coverage checker** としては残してよいですが、**見出しごとの本文生成器としては降格**してください。citeturn24view0turn3view0turn21search7
