## 1. はじめに：コトミガキとは

**ひとことで言うと**：Webサイト1ページを入力すると、「検索エンジン（SEO）」と「AI検索・AI回答（AIO/GEO）」の両方の観点からスコアと改善提案を自動で出すサイト診断ツール。

- 通常のSEOツールが見ていない「ChatGPT・Perplexity・Google AI Overview にどう引用されるか」を定量的に診断する点が最大の特徴
- スコアだけでなく、**法務リスク（特商法・景表法・ステマ規制）・アクセシビリティ・構造化データ**まで1回の分析でまとめて診断する統合型ツール
- 結果はWeb画面（NiceGUI）で確認でき、CSV／Markdown／Word／PDFとしても出力できる

**想定ユーザー**：自社サイトを運用する事業者、Web制作・SEO支援会社、コンサルタント（=非エンジニアにも分かる言葉で結果を出す設計になっている）

## 2. 全体処理フロー（1回の分析で起きること）

入力は **URLひとつ** だけ。内部では以下の順で処理が走ります（実装の中核：`core/engine/orchestrator.py :: SEOAIOAnalyzer.analyze_url`）。

```
①URL受付・robots.txt確認
   └ 一般クローラーが拒否されていれば、ここで安全に処理を中断

②HTML取得・文字コード判定・サイトマップ解析
   └ 本体ページに加え、特商法/会社概要/FAQなど「優先ページ」も
      自動で複数枚クロールして法務チェック精度を上げる（階層クロール）

③業界自動判定／検索意図推定／プラットフォーム(CMS)自動判定
   └ 「医療」「EC」「不動産」など14業種を自動推定し、以後の判定基準を調整

④SEO分析            … 機能A
⑤AIO分析            … 機能B（コトミガキの中核）
⑥統合スコア計算       … 機能E（SEOとAIOを1つのスコアに統合）
⑦サイトヘルス統合チェック
   ├ 法務・コンプライアンス … 機能H
   ├ 構造化データ        … 機能F
   ├ OGP/セキュリティ/アクセシビリティ … 機能I
   └ FAQ検出・提案        … 機能G

⑧引用スニペット抽出 … 機能D
⑨エンティティ・知識グラフ分析 … 機能C
⑩レポート整理・保存 … 機能K・機能L
⑪画面表示          … 機能M
```

進捗は11段階でリアルタイムにUI側へ通知され（`初期化→URL取得→本文解析→SEO評価→AIO評価→法務・規約チェック→レポート整理→完了`)、ユーザーは処理中も状況を把握できます。

## 3. 機能A：SEO分析

**ひとことで言うと**：検索エンジン（Google等）が評価する従来型のSEO項目を採点する、いわば「土台」の機能。

### 目的
AIOやGEOがいかに進化しても、検索エンジンに正しくクロール・インデックスされることが大前提。タイトル・見出し・速度・リンク構造など、SEOの基本健全性をまず可視化する。

### 入力
- 取得したHTML全体、レスポンスヘッダー、サイトマップ情報

### アルゴリズム（評価軸）
- 基本情報：title・meta description の有無と文字数の適正範囲
- 構造：見出し階層（h1〜h3）、内部リンク数・外部リンク数、画像のalt充足率
- コンテンツ：本文量、text/html比率
- 技術基盤：HTTPS、canonical、viewport、構造化データの有無
- ページ体験：LCP/CLS（Core Web Vitals 系の推定値）
- 国際対応：hreflang、x-robots-tag
- 内部リンク健全性：孤立ページ・被リンク不足ページの検出（`core/seo/link_audit.py` 系）
- メディア発見性：画像・動画がサイトマップ等から発見可能か

### 出力
0〜100に正規化した `seo_score` と、項目別の `scores` 辞書、即実行アクション（`immediate_actions`）

### UIでの見え方
「SEOタブ」で、タイトル/メタディスクリプション/見出し構造/リンク品質/Core Web Vitalsをカード形式で表示。スコアが低い項目には改善アクションが添付される。

## 4. 機能B：AIO分析（AI最適化診断）— 最大の差別化機能

**ひとことで言うと**：「このページはAI（ChatGPT・Perplexity・Google AI Overviewなど）に引用されやすいか」を11個の指標で定量化する、コトミガキの核となる機能。

### 目的
従来のSEOは「検索順位」を最適化するが、AIOは「AIの回答に引用される確率」を最適化する。両者の評価軸は大きく異なるため、専用のスコアリングエンジンを持つ。

### 入力
本文テキスト、HTML構造、robots.txt（AIクローラー許可状況）、応答速度

### アルゴリズム：AIO raw score（11指標・加重合算、合計100%）

| 指標 | 重み | 何を見ているか |
|---|---|---|
| PID（命題密度） | 20% | 助詞・代名詞を除いた「内容語」の比率。情報の濃さを測る |
| HTML構造 | 15% | セマンティックタグ・見出し階層・リスト/表・FAQ構造 |
| エンティティ重要度 | 12% | 固有名詞の多様性・偏りのなさ・出現位置 |
| 技術指標（Soft Tech） | 10% | HTTPS、応答速度 |
| 文中E-E-A-T | 8% | 資格・著者明示・組織・一次情報の文中表現（日本語専用パターン） |
| Citation readiness | 10% | 結論先出し・データ密度・簡潔さ・出典明記など6軸 |
| Contextual freshness | 6% | 更新日が機械判読可能な形（JSON-LD等）で示されているか |
| AEO patterns | 5% | 「〜とは、〜である」のような定義文が見出し直下にあるか |
| Entity linking | 4% | 固有名詞がWikidata等と紐づけ可能か（後述・機能C） |
| GEO TL;DR | 5% | 冒頭50〜150字の要約ブロックの有無・質 |
| GEO 統計密度 | 5% | 数値・統計表現の密度（GEO研究で実証された+30〜40%効果） |

**具体的な判定ロジックの例**：

- **PID（命題密度）**：日本語形態素解析エンジン「Sudachi」で分割し、名詞・動詞・形容詞（代名詞は除く）の比率を計算。0.65以上で満点。
- **文中E-E-A-T**：「一級建築士」「弁護士」等の資格パターン、「監修：山田太郎」等の著者明示パターン、「実際に試した」等の一次情報パターンを正規表現で検出し、0〜10点で採点。
- **GEO TL;DR**：冒頭500字に「まとめると」「この記事でわかること」等の明示ラベルがあれば+3点、先頭3000字以内に箇条書きがあれば+2点、冒頭段落が50〜150字の最適長なら+2点（5点満点）。
- **GEO統計密度**：「30%」「5年間」のような数値+単位表現を正規表現でカウントし、1,000字あたりの密度で high/medium/low を判定。出典表記（「出典：」等）があれば+1点ボーナス。

### スコアとは別軸：プロバイダ別「公開条件」チェック（gate）

AIO raw scoreに加点・減点しない別軸として、**4つのAI検索エンジンそれぞれの「最低限の公開条件」**を厳格にチェックする：

| プロバイダ | 必須クローラー | 主なブロック要因 |
|---|---|---|
| Google | Googlebot | noindex / nosnippet / max-snippet=0 |
| OpenAI Search | OAI-SearchBot | robots.txtでの拒否 |
| Perplexity | PerplexityBot | robots.txtでの拒否 |
| Claude Search | Claude-SearchBot | robots.txtでの拒否 |

それぞれ「通過／注意／要対応」の3段階で判定し、`GPTBot`・`Google-Extended`・`ClaudeBot`・`CCBot` 等は「informational note」（参考情報。学習用クローラーであり検索掲載条件には直結しない）として別枠で表示する。**この区別（公式要件 vs 内部ヒューリスティック）を厳密に分けているのが本ツールの設計上の重要ポイント。**

### 出力
`total_score`（0-100）、11指標の内訳、`provider_readiness`（4プロバイダの状態）、優先度付きの改善アクション（`immediate_actions`）

### UIでの見え方
「AIOタブ」で円グラフ的にスコア分解を表示し、プロバイダ別ステータスをバッジ（通過/注意/要対応）で表示。改善アクションには「Google向け」「Perplexity向け」のようにプロバイダ名が明示される。

## 5. 機能C：エンティティ認識・知識グラフ・Wikidata連携

**ひとことで言うと**：ページ内の「固有名詞（会社名・人名・地名など）」をAIや検索エンジンが正しく識別できるよう、表記を整理し、Wikidataという世界共通のID（QID）と紐づける機能。

### 目的
「テスラ」と「Tesla」と「テスラ社」が別物として扱われると、AIはエンティティの重要度を正しく評価できない。表記を統一し、外部の知識ベースと接続することで、AIにとっての「このページが何について書かれているか」の理解度を上げる。

### アルゴリズム（5段階処理）

1. **固有名詞抽出**：Sudachi形態素解析（C-mode）で固有名詞（人名・地名・組織名等）を抽出
2. **カテゴリ別重み付け**：人名=1.2、地名/組織=1.0 等、E-E-A-Tへの影響度に応じて重みを変える
3. **補完辞書**：Sudachi辞書に載っていない新語（ChatGPT、AIO、Core Web Vitals等）を専用辞書で補完
4. **表記ゆれ正規化**：「グーグル」→「Google」、「ツイッター」→「X」のように、カタカナ表記・旧名称・大文字小文字を統一し、同一エンティティとしてグルーピング
5. **Wikidata QID連携**：上位3エンティティのみ、Wikidata APIで検索しQID（例：Google → Q95）を取得。SQLiteに30日キャッシュし、API呼び出しは0.5秒間隔に制限（負荷配慮）。「こと」「もの」「商品」等の一般語はブラックリストとして検索対象から除外。

### 出力
エンティティリンキングスコア（0-1）、検出エンティティ一覧、表記ゆれ警告（例：「Google」「グーグル」の統一を推奨）、Wikidata連携結果

### UIでの見え方
「エンティティリンキング」セクションで検出語句一覧とスコアゲージを表示。表記ゆれがあれば「『グーグル』を『Google』に統一を推奨」のように具体的に提示。

## 6. 機能D：引用スニペット抽出（AI引用対策）

**ひとことで言うと**：ページ本文の中から「AIが引用しやすい1文」を自動で見つけ出し、AIの音声読み上げ用マークアップ（speakable）まで生成する機能。

### 目的
ChatGPTやGoogle AI Overviewが回答を生成する際、ページ全体ではなく「特定の1〜2文」を引用元として使う。どの文が引用されやすいかを事前に把握・最適化できれば、AI経由の流入（GEO/AIO）で優位に立てる。

### アルゴリズム

1. 本文を句点で文単位に分割し、30〜200文字の文のみを候補化（「詳しくはこちら」等のCTA文言は除外）
2. 各文に以下のパターンで加点（複合スコア）：

| パターン | 加点 |
|---|---|
| 定義文（「〇〇とは」） | +30 |
| 数値・統計（「30%」「5年間」） | +25 |
| 結論・要約（「つまり」「まとめると」） | +20 |
| リスト冒頭（「以下の3つ」） | +15 |
| 最適な文長（60〜120字） | +10 |
| カタカナ専門用語2語以上 | +5 |

3. スコア降順で上位3文を選出し、重複（先頭50字が同じ文）は統合

### 出力
- 上位3文とそのスコア・理由
- JSON-LD `speakable` マークアップ（W3C仕様、AI音声読み上げ対応）
- そのままページに貼れるHTMLスニペット例

### UIでの見え方
「引用候補」タブで上位3文をスコア付きカードで表示し、コピーボタンでHTMLをそのまま取得できる。

## 7. 機能E：統合スコアリング（検索意図α・業界補正・YMYL・GEOスコア）

**ひとことで言うと**：機能A（SEO）と機能B（AIO）、2つの異なるスコアを「このページの検索意図」に応じた配分で1つの総合スコアに統合する、コトミガキの“頭脳”部分。

### 目的
SEOとAIOを単純に50:50で混ぜるのは不正確。「このキーワードは買う意図が強いのか、調べる意図が強いのか」によって最適な配分は変わるため、検索意図に応じて重みを動的に変える。

### アルゴリズム

**①検索意図係数 α（SEO比率）**

| 検索意図 | SEO比率(α) | AIO比率(1-α) |
|---|---|---|
| 購買意図（transactional） | 70% | 30% |
| 情報収集（informational） | 20% | 80% |
| 指名検索（navigational） | 80% | 20% |
| 不明（unknown） | 50% | 50% |

統合スコア = `SEOスコア × α + AIOスコア × (1-α)`

**②業界による補正（YMYL以外）**
- B2B SaaS：AIO ×1.2／不動産：SEO・AIO ×1.1／EC：SEO ×1.3 のように業種特性に応じて補正

**③YMYL（Your Money or Your Life：医療・金融・法律等）の扱い**
- 重要な設計判断：**YMYL業界だからといって点数を掛け算で減点しない**（過去は1.2x/0.7x/0.5xの補正があったが廃止）
- 代わりに「YMYL文脈かつE-E-A-Tスコア4.0未満」の場合のみ、**注意喚起の警告文（点数には影響しない）**を出す
- 理由：日本語ページでの過剰減点を避けつつ、「公式な評価基準」と「内部ヒューリスティックな注意」を明確に分離するため

**④寄生コンテンツ疑義への軽いペナルティ**
- ドメインテーマと内容が大きく乖離している場合のみ、AIOスコアに×0.85の軽減（その他のペナルティは廃止）

**⑤GEO（内部診断）スコア**（100点満点、別建ての参考指標）

```
GEOスコア = TL;DRスコア/5 × 40点 + 統計密度スコア/10 × 35点 + E-E-A-Tスコア/10 × 25点
```
※ UIでは「内部診断（GEO）」と明示し、Googleの公式要件ではなく社内ヒューリスティックであることを表示

### 出力
`integrated_score`（統合スコア）、`seo_score`／`aio_score`、推奨バランス（このページは本来SEOとAIOをどの比率で見るべきか）、改善優先度リスト

### UIでの見え方
ダッシュボード上部に統合スコアを大きく表示し、「SEO優先」「AIO優先」のバッジと、推奨配分（例：SEO35%・AIO65%）を提示。

## 8. 機能F：構造化データ診断・提案

**ひとことで言うと**：検索エンジンやAIに「このページが何のページか」を正確に伝えるための専用タグ（JSON-LD/Schema.org）の実装状況を診断し、業種別のテンプレートまで自動生成する機能。

### 目的
構造化データがあると、検索結果にリッチリザルト（価格・評価・FAQ等）が表示されやすくなり、AIもページ内容を誤解しにくくなる。とはいえ実装は専門的なので、非エンジニアにも分かる形で「足りないもの」と「コピペで使えるテンプレート」を提示する。

### アルゴリズム

1. **抽出**：HTML内の`<script type="application/ld+json">`を全て解析
2. **サイトタイプ自動推論**：検出済みスキーマ→HTMLの特徴（カート文言、営業時間表記等）→URLの順に優先してEC／記事／地域店舗／企業のいずれかを推定
3. **業種別の推奨スキーマ提案**：例）EC→Product/Offer/AggregateRating、医療→MedicalOrganization/Physician、飲食→Restaurant/Menu
4. **検証スコア**：`(推奨スキーマの充足率 × 70%) + (必須フィールドの充足率 × 30%)` で0-100点化
5. **コンテンツ・スキーマ齟齬チェック**（LLM使用）：本文では「創業50年」と書いているのにJSON-LDに `foundingDate` がない、といった本文とタグの不整合をAIが検出
6. **プラットフォーム別実装ガイド**：WordPressなら「プラグインで5分」、楽天市場なら「出店者側では編集不可、自社ECで対応」など、難易度・手順・代替案まで提示

### 出力
検出済み／不足スキーマの一覧、コピペ可能なJSON-LDテンプレート、整合性スコア、プラットフォーム別の導入手順

### UIでの見え方
「構造化データ充足度」ゲージと、未実装スキーマへの「追加するとこう表示が変わる」というビジュアル説明、用語解説（i アイコン）付き。

## 9. 機能G：FAQ自動提案エンジン

**ひとことで言うと**：そのページの業種・訪問者タイプ・検討段階を自動推定し、「このページに今欠けているFAQ」を文章ごと提案する機能。単なるテンプレートの当てはめではなく、ページごとにオーダーメイドする。

### 目的
FAQ（Q&A形式）はAIに引用されやすい構造。ただし汎用テンプレートを置くだけでは効果が薄いため、ページの文脈（業種・URLの語・見出し・想定読者）から「このページに本当に必要な質問」を導き出す。

### アルゴリズム（3段階）

**①コンテキスト収集**：タイトル・meta・見出し・URLスラッグ・業種判定結果・想定読者ヒントなどを1つのコンテキストにまとめる

**②ペルソナ判定（8タイプ）**：EC購入者／来訪前訪問者／公共情報確認者／経営判断者／法人担当者／専門職／一般消費者など、キーワードの一致度をスコア化して最も可能性の高いペルソナを推定（例：「査定」「相続」「空き家」→不動産売却ペルソナ）

**③候補生成とリライト**：
- 業種共通の候補軸（信頼性・料金・利用フロー・対象者・アクセス等）に対し、本文中の該当キーワードのヒット数をスコアとして候補を採点
- 採用された候補は、ペルソナに応じて質問・回答文を書き換える（例：来訪者向けなら「初めて行く前に確認しておくべきことは？」、企業向けなら「どんな課題から先に役立つ？」）
- 公共・団体ドメイン（`go.jp`/`or.jp`等）は商用FAQより案内系FAQを優先するなど、ガードレールも実装

各候補には「確信度（high/medium/low）」と「外すと困るリスク（risk_if_wrong）」を付与し、AIが本文にない情報を断定しないよう注意書きも生成する。

### 出力
質問文・回答骨子・推奨設置位置・対応スキーマ（FAQPage等）・確信度を含むFAQ候補リスト、判定根拠（ペルソナ・マッチキーワード）

### UIでの見え方
「推定ペルソナ：不動産売却・査定（信頼度：中）」のように判定結果を明示し、各FAQ候補に確信度バッジと推奨設置場所を表示。

## 10. 機能H：法務・コンプライアンスチェック

**ひとことで言うと**：特定商取引法・景品表示法・ステルスマーケティング規制など、Webサイト運営で問われやすい複数の法令を自動チェックし、弁護士視点のコメント付きで提示する機能。

### 目的
表示義務違反や誇大広告は、消費者庁の措置命令・課徴金リスクに直結する。専門家でなくても「どこが危ないか」「どう直せばいいか」を具体的に把握できるようにする。

### アルゴリズム（チェッカー構成）

| チェッカー | 対象法令 | 主な判定ロジック |
|---|---|---|
| 特定商取引法チェック | 特商法第11条 | EC判定スコア（買い物かご・価格表示・決済キーワード等で0-100点）→ECと判定したら11の必須表示項目（販売業者名・所在地・電話番号・返品条件等）の検出有無を判定 |
| 景品表示法チェック | 景表法第5条 | 「業界No.1」「100%満足」等の優良誤認パターン、「通常価格→特別価格」等の有利誤認（二重価格表示）パターンを正規表現で検出し、業種別の厳格度（化粧品は1.5倍等）を加味してリスクスコア化 |
| ステマ規制チェック | 景表法施行規則（2023年10月施行） | アフィリエイトリンク・「おすすめ5選」等のコンテンツパターンからアフィリエイト可能性を判定し、「PR」表記の有無と表示位置の視認性（見出し内=最適、フッター=不十分）を評価 |
| 視認性チェック | 消費者契約法第4条等 | 重要情報の文字サイズ（12px未満は警告）、非表示テキスト、リンクの実質的な到達性をチェック |
| 非EC向け信頼性サマリー | － | 会社概要・連絡先・プライバシーポリシー等の有無を「リンク検出／本文検出／構造化データ検出」の3経路で確認 |

### 重複統合（証拠集約パイプライン）
複数チェッカーが同じ問題（例：「業界No.1」が3箇所）を検出した場合、文字列の類似度（閾値0.75）で重複をまとめ、最も信頼度の高い1件を代表として表示。検出件数・重要度別の統計（high/medium/low）も自動生成する。

### 出力
チェッカーごとの合否・適合率・検出項目リスト、重複統合後の優先度別サマリー（「重要：3件の高リスク項目があります」等のヘッドライン）、弁護士視点の法的根拠・改善例（Before/After）

### UIでの見え方
ECサイトでは特商法・景表法・ステマチェックをカードで表示し、専門家パネルで「法的根拠」「ベストプラクティス」「悪い例/良い例」を展開表示。非ECサイトでは法的義務がない前提で警告レベルを「参考」に格下げして表示する設計上の工夫がある。

## 11. 機能I：サイトヘルス（アクセシビリティ／OGP／セキュリティ）

**ひとことで言うと**：「誰にとっても使いやすいか」「SNSでシェアされたときに綺麗に見えるか」「通信は安全か」という、コンテンツとは別軸の“サイトの体力”を診断する機能。

### 目的
SEO・AIOのスコアが高くても、画像に説明がない／HTTPS未対応／SNSでシェアした時にサムネイルが出ない、といった基本的な不備はユーザー体験と検索評価の両方を損なう。

### アルゴリズム

**①アクセシビリティ改善スコア（0-100、9項目の重み付き合算）**

| 項目 | 重み |
|---|---|
| ランドマーク（main/nav/header/footer） | 16 |
| 画像のalt属性 | 14 |
| 見出し階層 | 12 |
| h1の有無 | 12 |
| 対話要素（a/buttonの名前） | 12 |
| フォームのラベル | 12 |
| html lang属性 | 8 |
| titleタグ | 8 |
| iframeのtitle | 6 |

本文量・構造タグ量が極端に少ないページ（空ページ等）は、検出の信頼性が低いため**スコア上限（35〜80点）を自動で設ける**設計になっている。また、同一の部品（共通ヘッダーのボタン等）が複数箇所にある場合は1課題として集約し、過剰減点を防ぐ。

実ブラウザ検査が利用できる環境（Node.js + Playwright + axe-core）では、色のコントラスト比やキーボード操作性まで含めた**実ブラウザ自動検出**を優先し、利用できない場合はHTML静的解析へ自動フォールバックする（fail-open設計）。

**②OGP/SNS最適化チェック**：og:title／og:description／og:image等の必須タグの有無と文字数適正、Twitter Cardの設定状況を検査し、`60点（必須タグ充足率）+20点（Twitter Card）+20点（画像）` でスコア化。SNSでの表示プレビューも生成。

**③セキュリティ基本チェック**：HTTPS対応（+30点）、セキュリティヘッダー充足率（+40点）、混合コンテンツ（HTTPSページ内のHTTP画像等）の有無（+15点）、フォーム送信先の安全性（+15点）でリスクレベル（低/中/高）を判定。

**④改善アクションへの変換**：検査結果は「非エンジニア向け（影響・見直し箇所・引き渡し先）」と「エンジニア向け（対象要素・作業内容・確認方法）」の2系統に自動で分けて表示。文言整形にはLLMを使うが、**優先順位・件数・重要度はルールベースで固定**し、LLMには決定させない設計（再現性の確保）。

### 出力
0-100スコア、課題グループ別の詳細リスト、優先アクション上位5件（非エンジニア版／エンジニア版）

### UIでの見え方
「見やすさ・使いやすさ改善スコア」として表示（正式な適合認証ではなく改善指標であることを明示）。実装・設定タブでは影響と引き渡し先のみ、技術タブでは対象要素やコードまで表示する、という情報の出し分けが特徴。

## 12. 機能J：SEO技術監査（業界判定／プラットフォーム検知／AIクローラー適合性／古いページ検出）

**ひとことで言うと**：ページの「裏側」（どの業種か、何で作られたサイトか、AIのクローラーが来られるか、昔のページが野良で残っていないか）を自動で調べる、診断の前提条件を整える機能群。

### アルゴリズム

**①業界自動判定**：タイトル・meta・本文を14業種のキーワード辞書（primary×3点／secondary×2点／specialized×5点の重み）でスコアリングし、最高スコアの業種を主業種、閾値（最高点の30%以上）を超えた業種を副業種として判定。信頼度は文字数に対するキーワード密度から算出。

**②プラットフォーム(CMS)自動検知**：HTML内の特徴的な文字列（`wp-content`→WordPress、`cdn.shopify.com`→Shopify等）のシグネチャマッチングで判定し、プラットフォーム別の改善ガイダンスに接続する。

**③AIクローラー適合性判定**：robots.txtでのAI検索系ボット（OAI-SearchBot、PerplexityBot等）のブロック状況、JSフレームワークの痕跡やtext/html比率からのSSR（サーバーサイドレンダリング）必要性推定、応答速度を合成して0-100の技術スコアを算出。ブロックを検出した場合は「AIO露出に重大な影響」という警告を出す。

**④古い公開ページ検出**：`data.html`/`company.html`等の固定候補と、既知URLのスラッグから生成した`◯◯.html`候補（最大24件）に実際にアクセスし、HTTP 200かつcanonicalもnoindexも無い場合は「旧サイトの残骸ページが検索やAI回答に紛れ込むリスクあり」として要対応フラグを立てる。

### 出力
業界判定結果（信頼度付き）、検知プラットフォーム、AIクローラー技術スコア、古いページの一覧と301リダイレクト等の対応方法

### UIでの見え方
ダッシュボードの基本情報欄に業界・プラットフォームを表示し、「技術」タブで古い公開ページ・AIクローラー状況を一覧表示。

## 13. 機能K：分析実行〜保存〜履歴比較（アプリケーション層）

**ひとことで言うと**：機能A〜Jの分析結果を受け取り、データベースへの永続化・優先アクションへの統合・過去分析との比較までを担う「裏方の司令塔」機能。

### アルゴリズム（処理フェーズ）

1. **分析実行**：一時的なエラーは自動で2回まで再試行
2. **優先アクション統合**：法務リスク・SEO改善・AIO改善・アクセシビリティ・ビジネス施策・技術施策など複数ソースの改善案を集約し、重複排除した上で「効果(impact)×緊急度(urgency)×工数(effort)」でランキング
3. **検索意図・ページ役割マップ**：タイトル・見出し・URL等から「このページは法務確認用か／料金確認用か／比較検討用か／信頼補強用か／集客用か」を自動判定し、本来あるべき内容に対する不足を特定
4. **UI用スナップショット生成**：分析結果全体（数MBの完全データ）とは別に、画面表示専用の軽量データ（スナップショット）を生成
5. **永続化**：SQLiteに スコア・課題数・URL等のメタデータを保存し、完全な分析結果はJSONファイルとして保存
6. **履歴比較**：同一URLの過去分析（最大12件）を取得し、スコアの前回比・課題数の増減を自動表示

### 出力
保存済みの分析結果（run_id付き）、UI表示用スナップショット、前回比較データ

### UIでの見え方
分析完了後、ダッシュボードの履歴テーブルに1行追加され、クリックすると詳細ページ（`/runs/{run_id}`）に遷移する。

## 14. 機能L：レポート出力（CSV／Markdown／Word／PDF）

**ひとことで言うと**：同じ分析結果を、用途別に4種類のファイル形式で書き出す機能。社内共有・印刷・データ加工など、使う場面に応じて最適な形式を選べる。

| 形式 | 用途 | 特徴 |
|---|---|---|
| CSV（優先アクション／履歴） | Excelでの管理・比較 | CSVインジェクション対策（`=`等のエスケープ）済み |
| Markdown | Notion/Wiki等での共有 | スコア・優先アクション・FAQ案・エンジニア向け作業票まで網羅した詳細レポート |
| Word（DOCX） | 経営層への共有・印刷 | フォーマット済みの報告書体裁 |
| PDF | 正式な納品・報告書 | 表紙→経営層向けサマリー→Before/Afterのリライト提案→プラットフォーム別実装ガイド→エンジニア向け技術詳細、という構成。**スコアの理由づけ文章はLLMが業種別の規制（薬機法・医療広告ガイドライン等）を踏まえて自動生成** |

### PDFにおけるLLM活用の特徴
スコアが低い理由を「タイトルが20文字と短いため」のような汎用的な説明にせず、**そのページの実データ（実際のタイトル文言や見出し）を引用しながら、業種特有の規制ポイントを踏まえて**説明文を生成する。OpenAI APIが使えない場合は自動でテンプレート文に切り替わる（fail-open）。

### UIでの見え方
詳細ページ上部に「レポート出力（Markdown/Word）」「優先アクションCSV」のダウンロードボタンを配置。

## 15. 機能M：UI画面構成（ダッシュボード／詳細ページ）

**ひとことで言うと**：上記すべての機能の結果を、迷わず読める1つの画面体験に統合するUI設計（NiceGUIで構築）。

### 画面構成

**トップ画面（`/`）**
- URL入力 → 任意で比較サイトURL・業界・プラットフォーム・SEO/AIOバランスを設定 → 「分析する」
- 分析中は11段階の進捗バーを表示
- 完了後は履歴テーブルに自動追加（検索・並べ替え・CSV出力対応）

**詳細ページ（`/runs/{run_id}`）**
分析結果は情報量が多いため、認知負荷を抑えるためにタブで分離：

| タブ | 主な内容 |
|---|---|
| 概要 | 統合スコア・最優先3件・前回比 |
| タスク/アクション | 優先順位付けされた改善アクション一覧 |
| ライティング | タイトル・メタディスクリプション改善案、FAQ候補、引用候補 |
| 実装・設定 | プロバイダ別状況、llms.txt、検索意図マップ（非エンジニア向け） |
| 技術 | エンジニア向け詳細（対象要素・確認方法・検出元） |
| 比較・履歴 | 前回比較・競合比較 |
| 法務 | 法令チェック結果・専門家コメント |

**設計上の一貫したルール**：「現状→改善方法→詳細→内部診断」という優先順で情報を並べ、固定的な参考情報は本文から折りたたみ（expansion）へ後退させる。専門用語にはiアイコンで簡易解説を付与する。

## 16. まとめ：機能マップと、競合に対する差別化ポイント

### 機能マップ（全体像の再確認）

```
                         ┌─────────────┐
            URL入力 ──→  │ クロール・前処理 │
                         └──────┬──────┘
                                ▼
       ┌─────────────┬─────────┴─────────┬─────────────┐
       ▼             ▼                    ▼             ▼
   機能A SEO分析   機能B AIO分析      機能J 技術監査    機能H 法務チェック
       │             │  （+機能C,D）        │             │
       └──────┬──────┘                    │             │
              ▼                            │             │
        機能E 統合スコアリング ◀────────────┘             │
              │                                          │
              ▼                                          ▼
        機能F 構造化データ／機能G FAQ提案／機能I サイトヘルス
              │
              ▼
        機能K 保存・履歴 ──→ 機能L レポート出力 ──→ 機能M UI表示
```

### 差別化ポイント（プレゼンで強調しやすい点）

1. **AIO/GEOという、まだ多くのSEOツールが対応していない軸を11指標で定量化**している（機能B）
2. **「公式なAI検索の公開条件」と「内部ヒューリスティックな注意」を明確に分離**して表示する誠実な設計（機能B・E）— 過大な断定をしない
3. **検索意図に応じてSEOとAIOの配分を動的に変える統合スコア**（機能E）。単純な平均ではない
4. **法務リスクまで一括診断**（特商法・景表法・ステマ規制）し、弁護士視点のコメントまで自動生成（機能H）
5. **ページごとにオーダーメイドされたFAQ提案**（ペルソナ自動判定、機能G）。テンプレートの当てはめではない
6. **非エンジニアとエンジニアで表示を出し分ける情報設計**が全機能で一貫している（機能I・K・L）
7. **YMYL（医療・金融等）でも過剰減点しない、慎重なスコア設計**（機能E）
