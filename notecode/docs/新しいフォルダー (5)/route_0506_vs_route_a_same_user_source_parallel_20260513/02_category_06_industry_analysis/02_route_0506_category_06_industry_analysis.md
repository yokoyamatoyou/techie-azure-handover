## 企業ブログが平坦になる理由

私たちがまず見る最大の課題は、文章が平坦になりやすいことです。LLMは統計的に尤もらしいトークンを優先しやすく、その結果、整っていても無味乾燥な文章になりがちです。

AIは文法や構造の修正には強みがあります。だからこそ、得意な修正と、共感や繊細なニュアンス理解が必要な領域を分けて考えます。

## 人間らしい文章をどう定義するか

私たちは、人間らしい文章を、語彙の多様さ、構文の変化、そしてゆらぎの集積として捉えます。ここでいうゆらぎには、執筆時の心理状態や認知負荷も含めます。

また、助詞の選び方、句読点の置き方、表記揺れのような細かな特徴も見ます。疲労を単なるノイズとして切り捨てず、人間らしさの一部として扱います。

## カテゴリ別のスタイルを設計する

私たちは、6つのブログカテゴリごとに、推奨漢字比率、MTLD水準、文末バリエーション、主要な言語的特徴を割り当てる表を前提に考えます。あわせて、config.jsonに基づく文体FSMで、文末表現や「サーバー／サーバ」「お勧め／おすすめ」のような表記揺れを制御します。

生成が進むにつれて疲労パラメータを上げ、構文を単純化し、語彙をより抽象的で反復的なものにする設計も提案されています。NLPで推論可能な感情状態と意図を構成概念として先に定義し、生成プロセスのソフト制約に置く流れです。

## 生成時に制約をかける

私たちは、制約をデコーディング段階でかけます。コントラスティブ・サーチは、対数確率に退化ペナルティを組み合わせて次トークンを選ぶ考え方です。

コントラスティブ・デコーディングは、expert と amateur の差分を使い、予測されすぎた表現を抑えて独自性を浮かび上がらせます。さらに、LogitsProcessorをカスタマイズすれば、文末反復、語彙多様性、禁止語、表記統一を生成時に動的に確認できます。

## 評価を軽くし、生成を速くする

私たちは、評価をBERTのような重いモデルではなく、Word2vec系の浅い特徴量、文長分散、品詞分布を使った並列再ランキングで進めます。asyncioでLLMとSudachi解析を並行実行し、数ミリ秒評価を目指す案です。

現状の1記事生成は約3分かかり、逐次的な後修正と外部ライブラリ解析のオーバーヘッドがボトルネックです。提案プロセスでは、60〜80秒への短縮を目標として置きます。

最後に、動的デジェネラシー・ペナルティ、認知疲労シミュレーター、インライン・マルチ制約デコーディング、HLCv2に基づく階層的一貫性確保の4方向を今後の追加案として整理します。改善の全体像を見渡しながら、次の検討につなげます。
